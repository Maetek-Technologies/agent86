# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

agent86, an agentic CLI harness, in Rust: the standard agent86. It began as a compatibility-first rewrite of the [Python implementation](https://github.com/Maetek-Technologies/agent86-python), now archived and no longer developed. Python was the behavioral oracle during the rewrite, and what the two share must stay compatible: CLI output streams, exit codes, `run --json` fields, TOML config semantics, and the session database (`state_json`), trace, prompt history, and keyring formats, so Python users can switch without losing anything. New behavior is designed here; record each difference from Python in the plan.

The CLI can run one text-only turn against any OpenAI-compatible provider (`agent86 --model provider:model run [--json] <goal>`), as an agent over the current directory: Python's system prompt, the ReAct loop, and `read_file`, `write_file`, `edit_file`, and `list_dir` (plus, beyond Python, `search_files` and `find_files`), with side-effecting calls passing through the approval gate. Python's ingress, egress, and observation guardrails apply. `run_command` and `python_exec` run under the sandbox executor, and `web_fetch` is guarded against SSRF. Each run is a session saved in Python's SQLite memory database and resumable with `run --session`; finished turns are recorded as episodes and recalled into similar later tasks; `delegate` runs sub-agents, which can be named specialists (`.agent86/agents/*.md` and built-ins, `/agent`, `run --agent`, in parallel or in git worktrees; [docs/subagents.md](docs/subagents.md)); and the agent can `remember` and `recall` facts (`agent86 memory` inspects the store), embedded with Python's default `all-MiniLM-L6-v2` run on candle from the shared Hugging Face cache. The flight recorder logs it to `~/.agent86/traces/trace.jsonl`. Embedders can declare a renderer, and the model then draws interactive UI as Google's A2UI 1.0 through `render_ui` (agent86UI, [docs/agent86ui.md](docs/agent86ui.md); the protocol crate is `crates/agent86-ui`). Configured MCP servers (stdio, streamable HTTP, or SSE) are started for each run and their tools registered next to the built-ins, and kept in step with drops, reconnects, and `list_changed` while the run goes on. `agent86` with no subcommand opens the interactive interface: Python's REPL (its slash commands, `@file` mentions, and prompt history) rendered inline in Claude Code's style, with an approval panel, a spinner, a live status line, and Escape or Ctrl+C to cancel a turn at its next safe point. `/config model` and `/config mcp` manage providers, keys, models, and MCP servers, writing config back with comments kept. `--plain`, `AGENT86_PLAIN`, or piped input gives Python's plain loop. `docs/PROJECT_PLAN.md` is the source of truth for current status, the next steps, the staged roadmap, known differences from Python, and the credential policy. Read it before starting feature work, and update it (plus `docs/FEATURES.md`, which holds the feature list and roadmap, and the README's Status section) when a stage lands. Keep both honest about what is and is not implemented.

## Commands

```bash
cargo test --workspace --all-targets         # all tests, both crates
cargo test -p agent86-core --no-default-features --lib  # the library without its optional features
cargo test -p agent86-ui                     # agent86UI's protocol crate, with the A2UI specification's own test cases
cargo test -p agent86-eval                   # the eval runner, and every eval task validated (needs Python)
cargo run -p agent86-eval -- run --model <provider:model>  # the eval set against a model (docs/evals.md; opt-in, uses the network)
cargo test --test compatibility              # just the compatibility suite
cargo test --test openai_provider            # provider tests against the local mock server
cargo test --test cli_run                    # end-to-end tests that run the agent86 binary
cargo test <test_name_substring>             # single test, e.g. cargo test model_refs_split
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings  # warnings are errors
cargo run -- --help
```

All three checks (test, fmt, clippy `-D warnings`) must pass. `unsafe_code` is forbidden in both crates (`[workspace.lints]`). MSRV is Rust 1.94 (`rust-version` in the root Cargo.toml's `[workspace.package]`, which both crates inherit, set by candle 0.11, which calls `__cpuid_count` outside `unsafe` on x86_64; before candle, `tokio`/`reqwest` and their URL dependencies set 1.88); avoid newer language/std features, and check a new dependency's `rust-version` before adding it. `.cargo/config.toml` makes the resolver prefer MSRV-compatible versions, but platform-specific dependencies (for example the Linux keyring stack) only build in CI, so watch the Linux and macOS MSRV jobs. Raising the MSRV is a deliberate change: update `[workspace.package]` and the CI matrix together. Dependency versions live once, in `[workspace.dependencies]`; each crate names the ones it uses.

CI (`.github/workflows/ci.yml`) runs tests on Linux, macOS, and Windows against both stable and the MSRV, with fmt and clippy on stable and, on every OS's stable row, `agent86-core`'s unit tests with `--no-default-features`, plus `cargo deny check advisories` (`deny.toml`; an exception needs a stated reason). `.github/workflows/scorecard.yml` runs OpenSSF Scorecard on pushes to `main` and weekly, publishing the result the README badge shows; Scorecard restricts that job while it publishes, so add no other steps to it. Every action is pinned to a commit SHA with its version in a comment, which Dependabot (`.github/dependabot.yml`) keeps current; pin any new action the same way. The required checks on `main` are named after the matrix (`ubuntu-latest / 1.94`), so changing the MSRV means updating branch protection too. Windows builds need the Visual Studio Build Tools C++ workload for `link.exe`.

## Architecture

The repository is a Cargo workspace of four crates (the fourth, `crates/agent86-eval`, is a development tool: the eval set's runner, `publish = false`, never built by the release workflow, which builds only the root package; [docs/evals.md](docs/evals.md)), sharing one version (`[workspace.package]`; the binary uses the library by path, so the two always build from the same checkout, and the release workflow and `npm/build.mjs` read the root manifest's first `version` line) ([docs/crate-split.md](docs/crate-split.md)):

- `crates/agent86-core/`: the library, the agent itself (everything under `crates/agent86-core/src/` below). `sdk` is its documented, stable surface; every other module is `pub` for the binary but `#[doc(hidden)]`, with no stability promise, so a type `sdk`'s signatures use is re-exported from `sdk` (`sdk::providers` holds the `Provider` trait, its types, and the adapters). Three default features: `os-keyring` (without it `secrets::OsKeyring` is the unsupported-platform stub, so lookups read as no key), `local-embeddings` (without it `memory::sentence_transformers` and `memory::hub` are gone and a `sentence-transformers:` spec falls back to the hash embedder with Python's `ImportError` note), and `agent86ui` (the `agent86-ui` dependency, `agent86ui`, `tools::render_ui`, `ToolContext::ui`, `TurnEvent::Ui`, and `sdk::Ui`; every use is behind `#[cfg(feature = "agent86ui")]`). It must never depend on the binary: nothing under it may name `ui`, `repl`, `acp`, `setup`, `keys`, `auth`, `update`, `history`, `mentions`, or `session_dirs`. Its tests (`crates/agent86-core/tests/`) are `sdk.rs`, which imports only from `agent86_core::sdk` to show the API stands alone, and `support/`, the shared mock server, which the root tests include with `#[path]`; `support::fixtures_dir()` finds the workspace's `tests/fixtures` from either crate.
- `crates/agent86-ui/`: agent86UI's protocol layer, Google's A2UI 1.0 for Rust ([ADR 0005](docs/adr/0005-agent86ui-a2ui.md)), depending on nothing else in the workspace (it must never name `agent86-core` or the binary). `Catalog` (loaded against `catalog_definition.json` and the specification's catalog rules; `Catalog::basic()`), `SchemaSet` (the envelope schemas compiled with `catalog.json` mapped to a catalog), `Validator` (a batch at a time, all or nothing: the schema check per message kind, then surfaces, ids, composition, cycles, function boundaries, and completeness under `Rules` (strict by default, as in the reference SDKs; `Rules::RELAXED` makes a missing root, dangling references, and orphans warnings), the reference SDKs' limits (`MAX_DEPTH`, `MAX_CALL_DEPTH`) and path syntax, legacy envelope keys moved to their `@` spellings before anything else (the batch is checked, applied, and typed normalized), and each function call checked against the catalog it resolves to (its `catalogId`, else the surface's default), with the specification's codes plus the reference SDKs' `RECURSION_LIMIT_EXCEEDED` and `CATALOG_NOT_FOUND`, and JSON Pointer paths, worded for a model), the typed `AgentMessage`/`RendererMessage`, and `runtime` (the headless surface runtime: `DataModel` with the shared pointer rules, the `formatString` template parser `expr`, `functions` (`Evaluator`, the basic catalog's functions, coercion, `Runtime::register` for embedder functions), `format` (`en-US`, matching `Intl`), `regex` (the A2UI dialect, parsed in full, the four safety rules, then translated for `fancy-regex`), and `surface::Runtime`: `apply`, `tree`, `input`, `dispatch`, `snapshot`, `capabilities`, `set_rules`). It validates with `jsonschema` (default features off) against the schemas vendored in `spec/` (Apache-2.0, upstream commit in `spec/UPSTREAM.md`) and served from memory by `MemoryDocs`, so nothing is ever fetched; never give it another retriever. `tests/conformance.rs` replays every case the specification ships (`tests/fixtures/v1_0/`, inside the crate so the published package keeps its tests), and `tests/runtime_conformance.rs` the shared SDK suites for the runtime, the validator, and the message processor (`tests/fixtures/conformance/`, YAML converted to JSON unchanged) under the upstream harness guide's strict rules (an unknown action or key fails; `UNSUPPORTED` entries that match nothing fail); refresh the schemas and those fixtures together, never one alone. Policy (which fields agent86 refuses, media rules) belongs in `agent86-core`, not here.
- `crates/agent86-eval/`: the eval set's runner (slice 0 of the local-model work; [docs/evals.md](docs/evals.md)), depending on no other workspace crate: it drives the built `agent86` binary (`run --json`, `--approval auto`) in a fresh workspace and isolated home per run, and scores each with the task's hidden check. The tasks are in `evals/tasks/<id>/` (`task.toml`, `workspace/`, optional seeded `setup/`, `check/`, `solution/`), Python with the standard library only and no network; every task must pass `agent86-eval validate` (its check fails untouched and passes with `solution/`), which `cargo test -p agent86-eval` runs over all of them. A run only ever takes the user's `[providers]` and `[pricing]` tables, never their MCP servers or skills.
- The root package, `agent86`: the binary (`src/main.rs`) and its surfaces (`src/ui/`, `src/repl.rs`, `src/acp/`, `src/setup.rs`, `src/keys.rs`, `src/auth.rs`, `src/update.rs`, `src/history.rs`, `src/mentions.rs`, `src/session_dirs.rs`). Its `src/lib.rs` re-exports every library module under its own name, so `crate::agent` inside the binary and `agent86::tools` in the root tests resolve as before the split. An item the binary needs from the library is made `pub` there (inside its hidden module), never duplicated.

- `crates/agent86-core/src/types.rs`: the provider-neutral vocabulary everything else will build on: `Role`, `AgentPhase`, `ApprovalMode`, `StopReason`, `ModelRef`, `ToolSpec`/`ToolCall`/`ToolResult`, `Message`, `CompletionRequest`/`Completion`/`CompletionDelta`, `Step`, `Usage` (implements `Add` for accumulation).
- `crates/agent86-core/src/provider/`: the model layer, ported from Python's `agent86/cognitive/`.
  - `mod.rs`: the object-safe `Provider` trait, `ProviderError`, and `provider_for_ref`, the factory. `anthropic` and `ollama` get their own adapters; `llamacpp` is the OpenAI-compatible adapter under its own name, keyless, with a local default URL; `vllm` and `lmstudio`, and any section with `adapter = "vllm"` or `"lmstudio"` (`ServerKind`, `server_kind`, beyond Python), are the same adapter under the server's name with an optional key (`key_optional`: sent when one resolves, a third key state every surface that sorts providers by key must know), local pricing, and the window the server reports (`remote_windows::vllm_context_window`; for LM Studio the loaded length, `lmstudio_context_window`, then `Provider::live_context_window` once a request has loaded the model, which `Harness::active_context_window` reads); `hints.rs` adds a hint to such a server's known error bodies (`ProviderError::HttpHint`, keeping Python's `HTTP <status>: <body>` first); any other provider section with a `base_url` becomes the OpenAI-compatible adapter. Providers implement only `stream()`, which returns a boxed stream of `CompletionDelta`s whose last item has `done = true` plus the full `Completion`. `complete()` is derived by collecting that stream, so streamed and non-streamed text always agree. Beyond Python, a section's `temperature` reaches the adapter through `with_temperature` (`Provider::temperature`, `None` by default and on Gemini), and `agent::request_temperature` picks a specialty's own first, then that, then Python's 0.0; send it through `temperature_json`, never `json!` on the `f32`. `ProviderError` messages mirror the Python wording and are stored already redacted.
  - `openai.rs`: the OpenAI-compatible SSE provider (OpenAI, OpenRouter, Groq, local servers). The stream is a hand-written state machine (`StreamState`) driven by `futures_util::stream::unfold`; dropping the stream drops the HTTP response, which is how cancellation works. Per-attempt accumulators live in `TurnState` and reset on every retry.
  - `anthropic.rs`: the Anthropic provider on the Messages API event stream. Python goes through the `anthropic` SDK, so the SDK's retry rules, fixed timeouts, and error text (the body printed as a Python dict, via `python_repr_value`) are part of the contract, alongside the adapter's prompt-cache markers and sampling fallback. Failures the SDK leaves unconverted get the wording Python's loop gives them. Tests use `tests/fixtures/anthropic/*.sse` with the mock server.
  - `google.rs`: the Gemini provider (beyond Python) on `generateContent` (`v1`, `streamGenerateContent?alt=sse`), the key in `x-goog-api-key` only, never the URL; `store` false unless the section sets it; no sampling parameters (Gemini 4 and 3.6+ ignore them, earlier Gemini 3 should keep the defaults); `includeThoughts` for thought summaries. `to_contents` maps the history (system messages to `systemInstruction`, tool calls to `functionCall` parts with the first per step signed, results to `functionResponse` parts after all of a step's calls, same-role contents merged by part lists, never by joining parts). A finish reason the loop cannot act on comes back as `stopped:<REASON>` (`provider::STOPPED_PREFIX`, shared with the OpenAI-compatible adapter's `content_filter` and structured `refusal` and the Anthropic adapter's `refusal`), which `agent.rs` announces once and does not ask about again. Tools go out as `parametersJsonSchema`, unchanged (the live check accepted every built-in and MCP-shaped schema); a name Gemini refuses (not starting with a letter or `_`) is declared as `_<name>` and mapped back (`gemini_name`). Each call's `thoughtSignature` and whether its id is Google's are kept in memory on the provider, by call id (`CallMeta`), and go back on the same part; nothing is added to `ToolCall` or `state_json`, and a call with nothing kept gets `SKIP_SIGNATURE`. `tests/google_live.rs` is the opt-in live check (`AGENT86_TEST_GEMINI_LIVE=1`, the key from the keyring).
  - `ollama.rs`: the Ollama provider: NDJSON from `/api/chat`, the same `unfold` state machine and retry rules as `openai.rs`, zero-cost usage, and Python's messages as preformatted `ProviderError::Message`s. Tests use `tests/fixtures/ollama/*.ndjson` with the mock server.
  - `retry.rs`: retryable statuses, `Retry-After`, and jittered backoff. A retry is never allowed once a text delta has been emitted, because the caller already saw that text.
  - `reasoning.rs`: `ReasoningFilter`, beyond Python, which the OpenAI-compatible and Ollama adapters run their reasoning through. It drops a line holding only an unopened closing tag (a host whose parser does not match the model's template leaves the model's own `</think>` in the reasoning), and notices when the raw reasoning has become one short unit repeated; the adapter then drops the response and finishes with stop reason `REASONING_LOOP`, which the loop announces and the empty-answer path picks up. `[providers.<name>.routing]` is sent as OpenRouter's `provider` field, to keep a model off such a host.
  - `capabilities.rs`: models that reject sampling parameters, and `context_window_with` (Python's `context_window_for`) for the status line; `remote_windows.rs` asks OpenRouter for a model's window, memoized and cached for 24 hours in Python's cache file. `context_window_for` is the variant that never touches the network.
  - `catalog.rs`: live model lists in Python's three shapes (OpenAI-compatible, Anthropic, Ollama), blocking on a thread of their own; every failure is a `CatalogUnavailable` with Python's message. `prefix_catalog_refs` and `catalog_has_ref` are the exact-prefix and exact-match rules the `/model` paths share.
- `crates/agent86-core/src/secrets.rs`: `redact()`, ported from Python's `secrets.py`. Run every response body or transport error through it before it reaches a `ProviderError`. Also `resolve_api_key()`: the `api_key_env` variable, then a `SecretStore` (`OsKeyring` in production; tests pass a fake or `NoSecretStore` through `provider_for_ref_with_store`, and must never touch the real keyring). On Windows `resolve_windows_credential` reproduces the Python `keyring` layout (`agent86`, then `<account>@agent86`); keep it that way so keys Python stored stay readable.
- `crates/agent86-core/src/vault.rs`: secure secret entry, beyond Python. `SecretVault` holds the secrets the user entered (`request_secret` in `crates/agent86-core/src/tools/secret.rs`, or `/secret NAME`), by name, for the session only; it lives on `ToolContext` (shared by clones, forks, and the recorder) with the prompt hook (`set_prompt`: the interface's panel via `UiEvent::Secret`, else the binary's `keys::terminal_secret_prompt` (moved out of the library in the split, since it reads hidden input through `keys::prompt_hidden`), installed by `setup` only when there is a terminal, which is also when the tool is registered; or, since 1.0.23, an ACP client with its own masked entry, through `acp::harness`'s `client_secret_prompt`). The rule is that the model never sees a value: `ToolRegistry::dispatch` redacts every result (content, error, and every string in its metadata), `run_turn_events` redacts the user's text, `StreamRedactor` the model's streamed text, and `Recorder` every event, each to `${secret:NAME}`. Exec tools get the values as environment variables after `scrubbed_env` (`Executor::run`'s `secrets`); Docker gets bare `-e NAME`. Beyond Python, the vault holds no value shorter than `MIN_SECRET_CHARS`, and `request_secret` refuses `RESERVED_NAMES` (names that would change how programs run); `accept` and `ask` say why with `NotSet`. Tools that `expands_secrets` (only `write_file` and `edit_file`) get `${secret:NAME}` in their arguments replaced by the value in `dispatch` (`tools::with_secrets`), and `build_preview` previews the expanded call, then redacts it. Any new path that carries tool output, user text, or model text to the model, the session, or the trace must go through the vault's redaction too. The user may also remember a secret for the project: `attach_store` gives the vault a `SharedStore` and the workspace path, `accept` applies a prompt's `SecretAnswer` (the value plus the remember choice, whose `Debug` hides the value), and the value lives in the OS keyring under account `secret:<md5 of the workspace path>:<NAME>` with a names-only index at `secret-index:<hash>`; `load_remembered` runs in `setup::assemble_with`, and `assemble` attaches the keyring only at a terminal, so piped and CI runs never touch it. Tests pass a fake store to `assemble_with` or `Repl::with_secret_store`, never the real keyring.
- `crates/agent86-core/src/pricing.rs`: `PriceTable`, ported from `pricing.py` (built-in rates, local providers at zero, dated-snapshot matching, cache rates, `[pricing.models]` overrides). Python keeps overrides in a module global; here the table is passed to the provider with `with_pricing`, and usage is priced under the full `provider:model` ref (a deliberate fix, see the plan). Unknown models cost `0.0` but must display as `cost n/a`, so ask `is_priced` before showing a dollar figure.
- `crates/agent86-core/src/pyjson.rs`: `python_float`, a `serialize_with` that writes floats exactly as Python's `json.dumps` does (`1.44e-05`); use it on every `f64` field that reaches `run --json`. `python_json_dumps` reproduces `json.dumps` text (separators, key order, `ensure_ascii`), for tool previews and the arguments sent back to the model. `serde_json` is built with `preserve_order`, so maps keep insertion order everywhere.
- `crates/agent86-core/src/prompt.rs`: the system prompt. `BASE_IDENTITY` must stay byte-identical to Python's `_BASE_IDENTITY` (the environment line after it is agent86's, and beyond Python names the platform, `run_command`'s shell, and the Python command: `platform_note`); `tests/system_prompt.rs` compares it with `tests/fixtures/prompt/base_identity.txt`, which was extracted from the Python source with `ast` (parsed, never executed). Re-extract it the same way when the reference changes.
- `src/keys.rs`: `agent86 keys set|delete`. All checks (known provider with `api_key_env`, non-empty single paste) run before the keyring is written, so CLI tests cover only refusals; never add a test that stores a real key. Hidden input uses `rpassword`, except under MSYS (`MSYSTEM` set, i.e. Git Bash), where console prompts cannot read input and `stty -echo` is used instead. On Windows the store leaves `UserName` empty for credentials created under an explicit target, so `CredentialVault::write` must set it explicitly; `tests/os_keyring.rs` has an opt-in live round trip that catches this.
- `src/auth.rs`: `agent86 auth`, beyond Python: choose a keyed provider, read the key through `keys::read_key`, store it as `keys set` does. It is what ACP's `terminal` authentication method (`acp::AUTH_METHOD_ID`) launches, which the ACP registry requires; tests pass a fake `SecretStore`.
- `crates/agent86-core/src/tools/`: the tool layer. `Tool` (`execute` returns `Result<ToolResult, ToolError>`; the provided `run` turns failures into `ok = false` results with Python's messages: `Invalid arguments for '<tool>': <field>: <msg>` or `<PythonException>: <msg>`). `Arguments` reproduces pydantic validation messages. `SandboxPolicy::resolve_within` is the workspace jail; every path a tool touches must go through it. Its `resolve` follows symlinks whose target is missing too (`read_link`), so a dangling link cannot carry a write outside. `parameters()` must equal what pydantic generates for the Python `Args` model: `tests/fixtures/tools/schemas.json` was produced by a local script mirroring those models (not by running the reference repo), so regenerate it the same way when adding a tool. Beyond Python, `ToolRegistry::dispatch` repairs a JSON-string argument (`repair_arguments`): when a property's schema accepts an array or an object and not a string, and the model sent a string that parses as that kind, the parsed value is used; the call the loop keeps is the model's own, and the result's `args_repaired` metadata becomes a `tool_args_repaired` trace event; a string that looks like such JSON but does not parse is left alone, and when the call then fails `unparsed_json_hint` adds where it broke to the error (`Harness::record_repair`, also called for sub-agents). `search.rs` is `search_files` and `find_files`, beyond Python: the `ignore` crate's walker (ignore files with or without git, hidden files searched, version-control metadata never), symlinks never descended and linked files read only inside the walk's jail root (`SandboxPolicy::root_of`), `/`-separated workspace-relative paths in path order, and every cut noted with how to narrow the search; registered in `default_registry`, not `builtin_registry`, which stays Python's list.
- `crates/agent86-core/src/approval.rs`: `ApprovalGate` (`auto`/`ask`/`deny`; the mode sits behind a lock, read with `mode()` and changed with `set_mode()`, so the interface can switch it mid-turn) and the terminal prompt, whose text (`prompt_text`) shows control characters through `escape::show_controls`. `ApprovalPreview` carries the tool's `preview_lexer`, as Python's does. The prompt is only installed when stdin is a terminal; without one, `ask` declines, and that is what makes piped and CI runs safe. Approvals of the main loop's calls are settled on the loop's thread before any tool runs (`Harness::resolve_call`), never inside the parallel read path; a sub-agent's calls, including those of sub-agents running in parallel, are decided on their own threads, and every question (approval, limit, secret) goes through `ApprovalGate::queue` (`PromptQueue`), one at a time, first in first out, declined once the turn is cancelled; `PromptQueue::ask` takes a `Question` describing it (never arguments or a secret's name), and `set_watcher` is told what is asked and what waits. A sub-agent's preview carries `ApprovalPreview::asker` (`Asker::of`, from `ToolContext::subagent`, a `subagent::SubagentRun` kept current as it runs). Beyond Python, a call whose `Tool::guarded_target` is set (a file tool writing where `SandboxPolicy::guarded` says agent86's own configuration or skills live) is asked about in every mode but `deny`, with `ApprovalPreview::warning` shown above the detail.
- `crates/agent86-core/src/guardrails.rs`: Python's scanner regexes, verbatim. `tests/guardrails.rs` compares the pattern strings with `tests/fixtures/guardrails/scanners.json` (extracted from the Python source with `ast`) and the scan and redaction results with CPython's `re`; keep both checks passing when patterns change. In `egress = "redact"` mode the loop must never emit unredacted model text, so streaming is buffered per step.
- `crates/agent86-core/src/tools/sandbox.rs`: the executors. `run_subprocess` must keep three properties: the scrubbed environment (`env_clear` plus `scrubbed_env`, never inheriting), a deadline covering both process exit and pipe EOF, and a process-tree kill on timeout. Each pipe is read through `capture`, which keeps `MAX_CAPTURE_BYTES` and drains the rest, and a timeout collects them with `drain`. The Docker command drops every capability but the six writing the user-owned workspace needs; keep one `--cap-add` per capability. Child working directories go through `plain_path`, because `cmd.exe` cannot use a `\\?\` path. `tests/exec_tools.rs` runs real processes on every platform.
- `crates/agent86-core/src/tools/web.rs`: `web_fetch`. Every hop must go through `vet_url` before a connection, and the client must be pinned to the vetted addresses (`resolve_to_addrs`); never enable automatic redirects. `block_reason` mirrors Python 3.12 `ipaddress` and is checked against `tests/fixtures/web/golden.json`, except the ranges refused beyond Python (`BEYOND_PYTHON` in `tests/web_fetch.rs`); the client is built with `.no_proxy()`, since a proxy would resolve the host itself. Tools run synchronously inside the harness runtime, so the fetch runs on a scoped thread with its own runtime.
- `crates/agent86-core/src/difflib.rs`: a port of CPython's `SequenceMatcher` and `unified_diff`, plus Python's `splitlines`. File-tool diffs must come from here, not a diff crate, because other algorithms group hunks differently. `tests/fixtures/tools/write_tools.json` holds CPython-generated diffs.
- `crates/agent86-core/src/config.rs`: layered TOML config: built-in defaults (a TOML string), the user file, the project file, `AGENT86_MODEL`, then `--model`, deep-merged as `toml::Table`s before deserializing. Unknown sections and keys are ignored, as Python's pydantic models allow. `ConfigPaths` and `Overrides` are explicit parameters so tests never touch the real home directory. Providers keep config order (an `IndexMap`), as Python lists them.
- `crates/agent86-core/src/trust.rs`: project-file trust, beyond Python. `ConfigPaths::project_trust` says whether the project file's settings outside `TRUST_FREE` count; `discover()` starts `Restricted`, and `main` calls `trust::decide` (the remembered SHA-256 in `~/.agent86/trusted-projects.json`, `--trust-project`/`AGENT86_TRUST_PROJECT`, or a `[y/N]` at a terminal) before loading. `load_config` drops the rest and lists them in `Config::untrusted`. A new config setting needs trust unless it is added to `TRUST_FREE`, which must only hold settings that cannot run anything, move keys or data, or loosen approvals. Tests build `ConfigPaths` with `ProjectTrust::Trusted`, and the CLI and REPL harnesses set `AGENT86_TRUST_PROJECT=1`. Conventions encoded in the types that must be preserved:

- Serde JSON is the wire format and must match the Python field names and values exactly. Enums use `rename_all = "snake_case"` (e.g. `end_turn`, `tool_use`). Optional/empty fields use `skip_serializing_if` plus `default` so absent and empty round-trip the same way Python does. `ToolResult.ok` defaults to `true` when missing.
- `ModelRef::parse` splits `provider:model` on the **first** colon only and trims whitespace (`local:model:variant` gives model `model:variant`).
- When a provider returns malformed tool-call JSON, the raw string is kept under `INVALID_TOOL_ARGS_KEY` (`"__invalid_json__"`) in `ToolCall.arguments` rather than failing; read it back with `ToolCall::invalid_arguments()`. Beyond Python (ADR 0006): an adapter sends such a call back in the history as `ToolCall::replay_arguments()` (`{}`), never with the key; the loop first tries `Harness::repair_broken_calls` (dropping closers that match nothing, `src/broken_json.rs`, the repaired arguments replacing the raw text on the call), and the observation for one still broken says where it broke (`broken_json::describe`).

## Working rules

- Shell commands from the Bash tool collapse doubled backslashes, so write source or fixtures containing backslash escapes with the Write or Edit tools, never via heredocs.

- Add behavior only together with tests that make the contract explicit. For behavior shared with Python, compare observable behavior; don't copy Python implementation details. Design around Rust async ownership and cancellation instead of literally reproducing Python's threads and event loops.
- Work in small vertical slices that follow the plan's next actions. Changes beyond what the Python version does are welcome when they fix real problems, and each is recorded in the plan as a deliberate difference.
- `run --json` must emit exactly one JSON object on stdout with errors on stderr. Keep the field names `session_id`, `output`, `steps`, `usage`, `turn` from the start.
- Default tests must need no credentials or network: use recorded fixtures (e.g. SSE) and local mock servers. Live provider smoke tests are opt-in only and stay out of normal CI.
- Secrets come from environment variables or the OS keyring only. They must never appear in config files, logs, errors, tests, or commits, and secret-shaped values should be redacted in error and trace paths.
- Don't claim performance improvements without benchmarks.
