Editors and other ACP clients now get the agent's forms and questions, and agent86 works better with local models: on a 35B local model at a 20k context window, sizing the context to the window took the eval set from 57 to 63 of 72 tasks in half the time, and telling the model it is on Windows cut the commands written for Linux from two runs in three to one in 216.

## Forms and questions in ACP clients

agent86-web and other clients of the [Agent Client Protocol](https://github.com/Maetek-Technologies/agent86/blob/main/docs/ACP.md) get agent86UI and `ask_user`, through two new extensions and a text version for clients that use neither.

- **A client that renders A2UI 1.0** names `com.maetek.agent86/a2ui` in its capabilities, with the basic catalog among its `supportedCatalogIds`, and the model can draw forms, choices, and confirmations there:
  - each message the model draws arrives as a `_com.maetek.agent86/a2ui/render` notification, already validated and with every held secret replaced by its placeholder;
  - when the model waits for an answer, the client gets `_com.maetek.agent86/a2ui/wait` and answers with the user's action, or with a dismissal;
  - a press after the turn goes back as `_com.maetek.agent86/a2ui/action`, which runs a turn on it, as a prompt does;
  - a loaded session draws its surfaces again after its history.
- **The agent's questions** (`ask_user`) reach every client, in one of three ways:
  - **its own form**: a client naming `com.maetek.agent86/questions` gets the questions as a `_com.maetek.agent86/questions/ask` request and answers with `{answers}` or `{dismissed: true}`;
  - **agent86's form**: a client with the a2ui extension gets the same form the terminal interface shows;
  - **text**: any other client gets the questions numbered, with each choice question's options lettered, and the turn ends there, so the user's next message is the answer.
- **Clients that draw nothing** are not offered `render_ui`, since Markdown reads better in a chat thread than a form turned into text, and the tool's part of the prompt costs a few thousand tokens a request. A session that drew surfaces elsewhere (in the terminal, the desktop app, or a client with the extension) shows those still up as text when such a client loads it.

`[ui] ask_user = "off"` turns the questions off in ACP too. Every message the ACP tests exchange was checked against the protocol's current v1 schema: 1,103 messages, none invalid; agent86's own extensions, which the schema does not cover, are 65 more.

## Local models

The local-model work ([docs/evals.md](https://github.com/Maetek-Technologies/agent86/blob/main/docs/evals.md)) starts with an eval set: 24 repository tasks in nine categories, each with a check the agent never sees, and a runner (`crates/agent86-eval`) that compares a model, or a setting, run against run. Every change below was measured on it with `cyankiwi/Qwen3.6-35B-A3B-AWQ-4bit` on vLLM, three runs of each task.

- **Context sized to the window** (`[limits] context_sizing`, on by default). Each tool result is cut to a third of the conversation's budget, keeping its start and end; older results are sent as short stubs once a request passes half the budget (the session keeps them whole); the budget shrinks for a model whose reported input tokens run above agent86's estimate; and on a small window the response's room is held to a share of it, unless you set the cap yourself. At a 20k window: 63 of 72 tasks with it, 57 without; 62 seconds a run against 118; no compactions against 33.
- **Compaction that keeps the task.** A long single turn can now be compacted inside itself, keeping your message as written and the progress so far under it; your message is never the part left out when a request is too big, and when anything is, the turn says so once; summaries no longer wear away each other's facts.
- **The platform in the system prompt.** The environment line now says where commands run: the platform, `run_command`'s shell, and the Python command (`python` on Windows). Before it, two runs in three on Windows spent calls on `python3`, `/home/...`, or `/usr/bin`; after it, one run in 216 did. The embedding API's default prompt says the same when its agent can run commands.
- **A stall nudge** (`[limits] stall_nudge`, on by default). When the same failing call is repeated with nothing changed, the same failure comes back three times, or the same thing is read three times with nothing changed, the model gets one short reminder to change its approach, and the turn shows `[stall] ...`. It changes few results on this model, but where it fires it saves time: one task took 172 seconds and 37k input tokens with it, against 522 seconds and 142k without.
- **A verification gate** (`[verify] command`, off by default, needing a trusted project). A turn that changed the workspace ends only once the command passes, or after `max_attempts` tries with the failure sent back to the model. `run --json` gains `verification`, before `final`. On this model and set it made no measurable difference, so it stays opt-in.
- **Temperature per provider and per specialty.** `[providers.<name>] temperature` and a specialist sub-agent's `temperature:` frontmatter (0 to 2) replace the 0.0 every request sends, for a model whose maker recommends another.
- **Content filters and refusals** from OpenAI-compatible providers and Anthropic are announced once as the provider stopping, instead of being taken for an empty answer and asked about again.

## Compatibility

The `sdk` API only gains: `AgentBuilder::verify`, `RunResult::verification` with `Verification` and `VerifyStatus`, and `Provider::temperature`, a provided method, so no code that uses it breaks. `run --json` gains `verification` only when a command is set. The session, trace, and keyring formats, and everything shared with the Python version, are unchanged; the trace only gains events (`context_age`, `context_trim`, `stall`, `verify`). The minimum supported Rust version is still 1.94.
