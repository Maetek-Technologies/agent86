When the agent needs something from you, it now asks with a form. A new tool, `ask_user`, takes a short list of questions from the model, and agent86 builds the form itself, so it always works, whatever the model: on the models measured, no model asked its questions in prose, and their calls were valid on the first try 102 times in 104.

## The agent asks through a form

```text
┏━ agent86UI · questions from the agent ━━━━━━━━━━━━━━━━━━━━━━━━━━━┓
┃ Your weekend trip                                                ┃
┃ Where are you leaving from?                                      ┃
┃ › [ Boston▏                                                    ] ┃
┃ What kind of trip?                                               ┃
┃   ( ) City and culture                                           ┃
┃   ( ) Outdoors                                                   ┃
┃   ( ) Other                                                      ┃
┃ Other, in your own words                                         ┃
┃   [                                                            ] ┃
┃   [ Send answers ]                                               ┃
┗━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┛
```

- **What the agent sends:** a title and up to 10 questions, each a choice (one option), multi (any of them), text, long text, number, yes/no, or date. Every choice question also offers "Other", with a field for your own words, so a list of options never traps you.
- **In the terminal interface** the form takes the keys at once: Tab or Up and Down move between questions, Space picks an option, typing fills a field, and Enter on **Send answers** sends. Send stays dimmed until every question not marked (optional) has an answer. Escape dismisses the form, and the agent is told not to ask the same questions again in that turn; Ctrl+C dismisses it and cancels the turn. Once sent, a copy goes into your scrollback.
- **In the plain loop** at a terminal (`--plain`, or when the interface cannot start), the same questions are asked as text, one at a time: type an option's number or your own words, Enter alone skips an optional question, and `/skip` stops answering.
- **In programs embedding `agent86-core`,** such as agent86-desktop, a `Ui` that answers waiting forms (`on_wait`) answers these too, with no new code: the form arrives as `TurnEvent::Ui` messages for surface `agent86_ask_<n>`, and its Send action is the answer.
- **The answers** come back to the agent keyed by question id, as numbers, `true`/`false`, `YYYY-MM-DD` dates, and so on, with which answers you typed rather than chose.
- **Settings:** `[ui] ask_user = "off"` turns it off, and the agent asks in its reply as before; a project file may set it without being trusted.

`agent86 run`, `run --json`, piped input, CI, and sub-agents never offer the tool, since nobody can answer, so their output is unchanged. ACP clients get it in 1.2.3, with agent86UI's ACP extension.

## Broken tool-call JSON, for every tool

This release began with a session where `claude-haiku-5.5` could not draw a seven-question form: twelve calls in a row, each with one `}` too many in its deepest nesting. Every tool now handles that better:

- **Where it broke.** The error for arguments that are not valid JSON keeps the old first line, then says at which character the JSON broke, inside which part (`messages[0].createSurface.components`), what was expected and found, and the text just before the break. The old message quoted only the first 200 characters, which were usually fine.
- **One closer too many is dropped.** If removing every `}` or `]` that closes nothing makes the arguments valid, the call runs with them, and the agent is told what was dropped. Nothing else is ever changed.
- **The failed call is sent back as `{}`,** not as a `__invalid_json__` key the model never wrote, which led it to blame "the wrong parameter name".
- **A second broken call in a row** is told to send less in each call, with the tool's own advice (`render_ui`: build the surface in parts).
- **The trace says why a call never ran:** arguments that did not parse, an unknown tool, and a refused approval are now `tool_call` events too.

## `render_ui`

- A button's `context` is optional: left out, the button sends every top-level value of its form, which removes the deepest nesting from every form the model writes.
- `{"path": "/x"}`, A2UI 0.9's way of binding a value, is read as `{"@path": "/x"}` (A2UI 1.0 would take it as a literal, so a button would send back `{"path": "/x"}` instead of your answer).
- The prompt asks for large surfaces to be built in parts, and for questions to go through `ask_user`, even when you ask for a form.
- Surface ids starting with `agent86_ask_` belong to `ask_user`'s forms and are refused.

## Measured

On the live check ([ADR 0006](https://github.com/Maetek-Technologies/agent86/blob/main/docs/adr/0006-ask-user.md)), across seven hosted models and two local ones (9B and 12B), no model asked its questions in prose. In the last round, 104 of 107 runs asked through `ask_user` and 102 of those calls were valid on the first try. The session that started this release, replayed, went from 2 of 6 valid first tries for Haiku with `render_ui` alone to every run with `ask_user`. [docs/agent86ui.md](https://github.com/Maetek-Technologies/agent86/blob/main/docs/agent86ui.md#asking-questions-ask_user) has the details.

Strict tool mode, planned for this release, moved to 1.3.0, since marking a tool strict changes the `sdk` API. The `sdk` API gains only `Tool::retry_hint`, a provided method, so no code that uses it breaks. The session, trace, and keyring formats, and everything shared with the Python version, are unchanged; the trace only gains events. The minimum supported Rust version is still 1.94.
