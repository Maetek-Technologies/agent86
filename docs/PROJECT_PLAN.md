## 1. Purpose

agent86 is an agentic harness on the command line: it connects to remote or local models and lets them use tools and skills. This repository is the standard agent86. It began as a compatibility-first Rust rewrite of the original Python implementation, which it replaced on 2026-10-30.

The rewrite did not translate the Python files mechanically. It built a coherent Rust implementation that kept the Python version's behavioral contracts, for:

- Distribution as one native executable, with no Python installation needed
- Fast startup and predictable resource usage
- Explicit, compiler-checked state transitions and provider-neutral types
- A unified async design for providers, tools, cancellation, and external processes

Performance and resource improvements should be measured rather than assumed. Model APIs, MCP servers, subprocesses, and I/O remain the dominant latency sources for many workloads.

## 2. Repository and the Python implementation

- **agent86:** [Maetek-Technologies/agent86](https://github.com/Maetek-Technologies/agent86), public
- **The Python implementation (archived):** [Maetek-Technologies/agent86-python](https://github.com/Maetek-Technologies/agent86-python), formerly `agent-86`, and `agent86` on PyPI

This repository started as `tdfleming/agent-86-rs`, under a personal account because organization OAuth restrictions then prevented creating repositories under `Maetek-Technologies`, and was transferred and renamed on 2026-10-30. GitHub redirects the old URLs.

The Python implementation was the behavioral oracle while the rewrite was under way, and the per-feature fixtures in `tests/fixtures/` were produced from its sources and from CPython. It is no longer developed. What the two share (the config files, the session and memory database, the trace format, the prompt history, and the keyring layout) stays compatible, so people can switch without losing anything; new behavior is designed here, and each difference is recorded under section 3.

### Known `run` differences from Python

- The system prompt is the identity, the environment line, the skills section, the MCP section when servers are live, and the turn's episodic recall note, as in Python.
- The environment line reports the Rust crate version. 1.0.0 matched Python's (`agent86 v1.0.0`); from 1.0.1, an interface-only release, the two differ, since they are versioned independently.
- Usage is priced under the full `provider:model` ref rather than the bare model id. Python prices with the bare id, so a `[pricing.models]` override keyed by the ref (for example `"openrouter:openai/gpt-4o-mini"`) marks the model as priced but never applies the rate, and the summary shows `$0.0000`. The ref is tried first and then the bare id, so every other case matches Python. Python should get the same fix.
- `agent86 keys` has no Python CLI equivalent; Python stores keys only from its interactive `/config model` screen (which the interface here also has). Re-saving an account on Windows does not leave Python's stale `<account>@agent86` copy of the old key behind.
- The missing-key error names the keyring entry to create (service `agent86`, account `<provider>`) instead of pointing at `/config model`.
- Reading keys that Python stored is verified on Windows against the `keyring` package's source, and live on 2026-10-26: a key saved with Python's `keyring set agent86 openrouter` was read by Rust and accepted by OpenRouter. On macOS and Linux the attribute layouts match by inspection but have not been tested against entries Python wrote. `tests/os_keyring.rs` is an opt-in check for any platform.
- `agent86 models`, `agent86 config`, `config path`, and `skills list` print plain aligned tables with Python's columns (Rich tables in Python), and `models` always reports the OS keyring as available. `config show` prints the merged config layers as JSON (built-in defaults for the modelled sections, the files, and the overrides), not Python's full pydantic dump with every default, as `/config` does.
- Rich wraps stderr at 80 columns when it is not a terminal; Rust does not wrap. stdout, including `--json` output (2-space indent, non-ASCII unescaped), is unaffected.

### Known REPL differences from Python

- A deliberate addition: both surfaces say when a newer release is out (checked at most once a day) and have `/update`; see the new-version notice under section 9.
- These apply to the plain loop (`--plain`, piped input, or a terminal that cannot host the interface). The interface's own differences are listed in the next section.
- Ctrl+C during a turn cancels it at the next safe point (`[cancelled]`, saved, traced as cancelled), which is what Python's full-screen app does with its cancel key. Python's plain loop instead raises `KeyboardInterrupt`, prints `interrupted`, and abandons the turn without closing or saving it. A running tool is never interrupted: the cancel takes effect when it finishes.
- Ctrl+C at an approval prompt does not decline; the prompt waits for an answer and the turn stops before the next call. Python declines.
- A cancel that lands after the model asked for tools but before any ran answers each call with `Not executed: cancelled.`; Python leaves those calls unanswered, which providers reject on the next request.
- `/config` prints the merged TOML layers (built-in defaults for the modelled sections, the config files, and overrides) as JSON, not Python's full pydantic dump with every default.
- `/config model` and `/config mcp` give Python's wording, pointing at the interface.
- `/models` always reports the OS keyring as available; Python checks for a usable backend. Its tables, `/sessions`, and the help list are plain aligned text (Rich tables in Python, with the same columns), and nothing is wrapped to the terminal width.
- `/model` switches the provider for later turns and pins it, turning triage routing off, as in Python.
- Answers are printed as plain text, as in Python's plain loop; the Markdown rendering behind `[ui] markdown` belongs to the full-screen app.

### Known interface differences from Python

- **The terminal title** (a deliberate addition, 2026-10-30): the interface sets the tab's title to `agent86 · <folder>`, with `✳` in front while a turn runs and `⚠` while the turn waits for an approval, a limit offer, or a secret, so another tab shows when it needs you. It is written only when it changes, from the drawing loop. On the way out (or a panic) the title is cleared, which gives the terminal back its own (Windows Terminal shows the shell again), and terminals with xterm's title stack restore the title saved at startup. The folder name is sanitized, so it cannot carry escape sequences. Python's interface leaves the title alone; under npm on Windows the tab otherwise reads `C:\WINDOWS\system32\cmd.exe`, from npm's `agent86.cmd` shim.
- **Inline, not full-screen** ([ADR 0001](adr/0001-inline-terminal-interface.md)): the interface renders in Claude Code's style rather than as Python's full-screen Textual app, though the text of every message, note, error, and summary is Python's. Differences that follow from that:
  - The conversation stays in the terminal's scrollback after exit.
  - Replies and tool calls are marked `⏺` and `⎿`.
  - The prompt is a bordered box.
  - The approval request is a numbered panel, not a modal with buttons.
- **Running tool calls:** a running tool call is shown in the live region until its result lands; Python shows nothing for it until then.
- **Ctrl+C and Ctrl+D:**
  - When idle, Ctrl+C clears a draft. On an empty prompt it asks `Press Ctrl+C again to exit` for two seconds; Python quits on the first press.
  - Ctrl+D on an empty prompt quits.
  - Ctrl+C while an approval panel is open declines the call and cancels the turn. Python cancels the turn and leaves the modal open until it is answered.
- **Pasting:** where the terminal delivers a paste as keystrokes (Windows), an Enter with more keys already waiting behind it counts as part of the paste. It adds a line instead of sending the draft.
- **Menus and pickers:**
  - A command typed in full is the one highlighted in the `/` menu, so `/mode` and Enter runs `/mode`. Python highlights the first match, which there is `/models`.
  - Tab in the `/` menu writes the command out, followed by a space, for its argument; Python's Tab moves focus away from the prompt.
  - Choosing a file in the `@` menu closes it; Python reopens the menu on the completed path.
  - The session picker has one box: typing filters and Enter picks the highlighted session. Python's filter box picks on Enter only when exactly one session matches.
  - The mode and model pickers also take the choice's number. Ctrl+C closes a picker, as Escape does.
  - A command run from the `/` menu goes through the same path as a typed one: it is echoed (Python doesn't echo a bare `/mode`, `/model`, or `/resume` picked from its palette) and the full command goes into the prompt history (Python records what had been typed, such as `/he`).
- **Rendering:**
  - A reply is rendered as Markdown a block at a time as it streams, not as one document when it ends; a block is only committed once complete, so the result is the same except where Markdown links a later block to an earlier one (reference-style link definitions).
  - The look is our own, not Rich's: `⏺` before the reply rather than an `agent86` label, `•` bullets, a gutter for code, a box-drawn rule under a table's header.
  - Fenced code is not syntax-highlighted; Python highlights it with Pygments. A command or snippet in the approval panel is shown plain; a diff is coloured.
- **Expanding tool calls:** Ctrl+O opens a full-screen transcript view with every tool call expanded, rather than expanding the last block in place; Ctrl+Shift+O (or `a`) toggles them all in that view.
- **Model management:**
  - The typed `/model <id>` fallback asks the catalog of the active provider's config section. Python's asks the adapter's name, which is `openai` for every OpenAI-compatible gateway, so on OpenRouter it fetched OpenAI's catalog with OpenRouter's key; its bare `/model` picker already uses the section, as this does. Python should get the same fix.
  - The catalog picker has one box: Enter with nothing typed picks the highlighted model, and a highlight moved with the arrows is picked as it is. Python's filter box takes Enter as submitting the typed text (nothing typed cancels).
  - A long model list (more than nine choices) can be narrowed by typing, and its rows are not numbered; Python's model picker has no filter. PgUp, PgDn, Home, and End move through any picker.
  - The connection test, key entry, and save steps are panels in place of the input box, with numbered choices; the save panel switches scope with the arrows or Tab and scrolls the diff with the arrows. A catalog that arrives during a turn or while a panel is open waits until both are done.
  - The key entry shows one dot per character; Python's password field does the same.
  - The OS keyring is always reported as available, so key entry never says the key will only be used for the test.
- **MCP management:**
  - Editing a server in place keeps it running with its new settings after the save. Python's edit stops the server its test just started (it removes the "original" even when the name is unchanged), so the edited server reports `0 tools live` until the next launch. Python should get the same fix.
  - A test closed before the server finished connecting stops the server once it does, and a test closed after connecting stops it too; Python leaves such a server running, unmounted, for the rest of the session. A failed save also stops the server its test started.
  - The 30-second budget is the connect's own deadline, so a server that never answers reports Python's `did not finish connecting within 30s (connect_timeout_s)` message rather than the test modal's `Timed out after 30s — no response.`
  - JSON syntax errors and wrong field types are reported with `serde_json`'s wording, not Python's `json` and pydantic messages; the validator's own messages (a missing command or URL, both set, an unknown transport) are Python's.
  - The form is a panel: Tab, Shift+Tab, or the arrows move between fields, Enter in a one-line field continues (as in Python), Enter in the JSON box adds a line, and Left or Right switches the transport. Shift+Tab in the form does not cycle the approval mode.
  - Errors written to the transcript after a failed test have key-shaped tokens redacted; Python redacts only the copy in the test modal.

### Known loop differences from Python

- A deliberate fix: a sub-agent whose final reply stops at the output cap continues, as the main loop's answer does (up to 3 times, each a step of its budget, with a `continuation` event), and the pieces are joined; one that reaches the cap before any text (a thinking model can spend all of it reasoning) answers `[sub-agent '<role>' wrote no answer: ...]`, and an empty answer is asked for once, then answered with the sub-agent's reasoning (`[sub-agent '<role>' gave no answer; its reasoning follows]`) or `[sub-agent '<role>' returned no text]`. Python returns the last reply as it is, so the parent gets a truncated or empty result it cannot tell from a real one.
- A deliberate fix: a sub-agent's requests carry the main loop's output cap (`max_output_tokens_for`, or the session's override). Python's sub-agents send none, so they get the provider's default (8192 on Anthropic, the server's own on an OpenAI-compatible endpoint), which neither `[limits] max_output_tokens` nor anything but the provider's `max_tokens` changes. On an OpenAI-compatible endpoint whose default is larger than 8192, a sub-agent's cap is now lower unless the cap is raised.
- A sub-agent's requests are fitted to a budget computed from the parent's system message and tools; Python reuses the budget of the parent's last request, which also counted that request's recall note.
- A route that cannot be built (an unknown provider, a missing key) fails the turn as a failed turn: it is saved in the `error` phase and traced with `turn_end`. Python raises before the turn is closed, so neither happens there.
- The window is looked up when the model is set (at start, on `/model`, and the first time a route is used), not before every request; a `[model.context_window]` change written by `/config` applies from the next `/model`.
- After a compaction mid-turn, the turn's start and a continuation in progress are re-indexed into the shorter history. Python keeps the old indices, which then point past where they should (a deliberate fix).
- The summary request can be cancelled; Python's blocks until it returns, and the turn stops at the next safe point.
- A cancel also wakes a response that has stopped streaming; Python checks only as each delta arrives.
- A deliberate addition: a final reply with no text is asked about once (`[no answer; asking the model again]`, one more step), and if the second is empty too the model's reasoning stands in for the answer (`[no answer; showing the model's reasoning]`) or the turn says `[the model gave no answer]`. Python ends the turn with the empty reply. The `empty_answer` trace event has no Python counterpart.
- A deliberate addition: the system message ends with the current local time and UTC, fixed per turn (and per sub-agent), followed by any recall note. Python's has no date. On Anthropic the system block's cache entry is rewritten each turn, as it already was whenever memory recalled something; the tools keep their own cache marker.

### Known approval differences from Python

- The approval prompt is written to stderr; Python writes it to stdout, which would corrupt `run --json` output when a terminal is attached. The preview is shown as plain text, without Rich's syntax highlighting.
- Ctrl+C at the `run` prompt ends the process; Python treats it as declining.

### Known guardrail differences from Python

- Python's `\s` also matches the control characters U+001C to U+001F; the Rust `regex` crate's does not, so whitespace made of those characters can split a pattern differently. Otherwise the patterns use the same Unicode-aware `\b`, `\d`, `\s`, and case folding.

### Known sandbox differences from Python

- `python_exec` runs the `python` (Windows) or `python3` (elsewhere) found on PATH; Python runs its own interpreter (`sys.executable`).
- On Windows, a child's working directory is passed without the `\\?\` verbatim prefix, which `cmd.exe` cannot use.

### Known `web_fetch` differences from Python

- HTML is reduced with Python's regex fallback. Python uses BeautifulSoup instead when its optional `web` extra is installed, which extracts text differently.
- Connections go to the addresses that were vetted, so a DNS answer that changes between the check and the connection cannot redirect the fetch; Python resolves twice.
- The default User-Agent names this repository and version.
- Charsets are decoded with `encoding_rs` (WHATWG labels), except Latin-1, which is decoded as true ISO-8859-1 as in Python. Transport error text differs from httpx's.

### Known session differences from Python

- `state_json` is valid in both directions but not byte-identical: Rust omits empty lists and nulls that pydantic writes, and writes floats in Python's `json.dumps` style where pydantic uses shortest-decimal notation.

### Known skill differences from Python

- `SKILL.md` frontmatter is always read with Python's built-in parser. Python uses PyYAML instead when it happens to be installed (the `local` extra brings it in), which reads full YAML: nested mappings, anchors, and YAML's own quoting and folding rules. The usual shapes (`key: value`, lists, `>`/`|` descriptions) read the same either way. Quoted strings are unescaped as PyYAML reads them (`\"` and `''`), since a typical install has PyYAML; Python's parser alone keeps the backslashes. Where PyYAML rejects one quoted string it falls back to the built-in parser for the whole file, but here only that string is left as written. `license` and `metadata` are not kept, since nothing reads them.
- `/skills` puts each name on its own line (bold cyan), with the description indented under it and any `allowed-tools` after it, instead of Python's one `name - description` line per skill, which is hard to read once descriptions run past the terminal's width. Rich escapes markup in the names and descriptions; here they are plain text.

### Known memory differences from Python

- sentence-transformers vectors differ from Python's in the last two or three `float32` bits (about 3e-7), so a score within about 1e-6 of a recall threshold can fall on the other side of it.
- Only BERT sentence-transformers models (Transformer, Pooling, and Normalize modules; absolute positions; GELU) are supported. Python runs any model sentence-transformers can; others fall back here with `(ValueError)`, as an unloadable model does in Python. Plain transformers checkpoints without `modules.json` are not supported.
- The fallback note names the Rust failure's Python counterpart (`OSError` for a missing or unreachable model, `ValueError` for an unsupported one) and drops Python's `pip install "agent86[local]"` hint.
- Downloads are anonymous: `HF_TOKEN` is not sent, so gated or private models cannot be fetched. Files are written straight into the snapshot (as `huggingface_hub` does on Windows without symlinks) rather than as `blobs/` with links, which both libraries read; `.no_exist` markers are not written.
- With `hf_offline = false`, every start asks the hub for `main` (Python's `huggingface_hub` also checks each file's ETag).
- Search is always the brute-force scan. Python uses `sqlite-vec`'s `vec_distance_cosine` when the extension loads, which computes in `float32`, so its scores can differ from the scan's in the last digits.
- Scores follow Python 3.12's `sum`; under Python 3.11 (which the reference still supports) the last bit can differ.
- A `recall` `k` written as an integer literal beyond 64 bits arrives as a float and is refused as too large; pydantic accepts any integer and the clamp makes it 20.
- The `memory` commands print plain aligned text instead of Rich tables, and stored text is printed as is; Rich would interpret markup in it.
- A negative `memory search -k` is a usage error; Python slices from the end.

### Known MCP differences from Python

- The JSON-RPC client and transports are hand-written rather than the MCP Python SDK, so transport-level error wording (connection failures, HTTP errors) differs; the user-facing messages for start failures, timeouts, drops, reconnects, and unavailable servers follow Python's.
- A streamable HTTP server is never detected as dropped (requests simply fail), which matches the SDK in practice; stdio and SSE drops are detected when the process exits or the stream ends.
- A reconnect failure's cause is the first line of the start-failure message rather than the SDK's exception text. A drop's cause never carries Python's `after <last transport error>` suffix, because a malformed line is skipped without being recorded.
- `notifications/message` (server logging) is ignored; Python sends it to its logger, which `run` does not show. Live notes (progress, resource updates, list changes) are recorded for a future REPL, and `run` prints none, as in Python.
- The `initialize` request names the client `agent86` with the crate version; the Python SDK sends its own client info.
- On Windows a bare `command` is looked up on PATH with `PATHEXT`, so `npx` finds `npx.cmd`, as the Python SDK does.
- `mcp list` and `mcp tools` print plain aligned tables with the same columns as Python's Rich tables.
- A deliberate addition: `[mcp.servers.<name>.defaults]` adds configured arguments to a tool's calls when the model leaves them out. Python has no such setting and ignores the table.

### Known flight-recorder differences from Python

- `trace show` prints a plain aligned table with the same columns as Python's Rich table.
- OpenTelemetry spans go over OTLP/HTTP with the JSON encoding (`<endpoint>/v1/traces`, `http://localhost:4318` by default), a deliberate choice that avoids a gRPC stack; Python's exporter speaks gRPC (`localhost:4317`) and falls back to HTTP with protobuf. The OpenTelemetry Collector, Jaeger, and Tempo accept both by default, but an endpoint that only serves gRPC receives nothing. `otel_endpoint` is a base URL that gets `/v1/traces` appended (unless it already ends with it); Python hands it to the gRPC exporter as the host.
- The resource carries `service.name`, `service.version` (the crate's), and `telemetry.sdk.language = "rust"`, not the Python SDK's `telemetry.sdk.*` values. `exception` events carry `exception.type` and `exception.message`, without a stack trace.
- A deliberate fix: read-only tool calls run in parallel are children of the turn span. Python runs them on a thread pool that does not carry the span context, so each becomes the root of a trace of its own.
- An export that fails is kept as the tracer's note and not printed; Python's SDK logs a warning to stderr. `otel = true` always exports here; Python needs its `otel` extra installed and is otherwise a no-op.
- Events for subsystems that are not ported (`cancelled` turns) are never written.
- `limit_raised` (a limit raised from the interface's offer) and `tool_args_repaired` (a JSON-string argument parsed into an array or an object) have no Python counterpart.

### Known tool differences from Python

- A deliberate addition: an array or object argument that arrives as a JSON string is parsed before validation when the schema wants an array or an object and not a string. Python's pydantic models reject it (`Input should be a valid list`), and so did this port until 2026-10-31. The `tool_args_repaired` trace event has no Python counterpart.
- I/O failures other than the handled cases report Rust's error text after Python's exception name (for example `PermissionError: Access is denied. (os error 5)` rather than Python's `[Errno 13] Permission denied: '...'`).
- Invalid UTF-8 is replaced per maximal invalid sequence (Rust's `from_utf8_lossy`) rather than per byte, so a run of bad bytes can yield fewer U+FFFD characters than Python.

### Known provider differences from Python

- Anthropic: the adapter speaks the HTTP API rather than going through the SDK. A stream cut short reports `ReadError:` with the transport error's text from `reqwest` (Python's loop names httpx's exception, usually `RemoteProtocolError`), and a malformed event names `serde_json`'s parse error after `JSONDecodeError:`. Tool input that is not valid JSON when its block ends is carried raw under `__invalid_json__`, as the other adapters do, where the SDK would keep whatever its partial-JSON parser salvaged. A `Retry-After` HTTP date falls back to backoff. The SDK's own request headers (`user-agent`, `x-stainless-*`) are not sent.

- Ollama: a stream cut short reports the transport error's text from `reqwest` rather than httpx's `<ExceptionName>: <message>`, and a malformed NDJSON line names `serde_json`'s parse error rather than Python's `JSONDecodeError` text; the rest of each message is Python's.

- Reasoning (a deliberate addition): Ollama's `thinking`, the OpenAI-compatible `reasoning_content` and `reasoning`, and Anthropic `thinking` blocks are read and reported apart from the text. Python ignores them, so its interface never shows reasoning and a model that answers only in its reasoning answers with nothing. See the empty-answer fallback under Known loop differences.

- Reasoning guard (a deliberate addition): in the OpenAI-compatible and Ollama adapters, a reasoning line holding only an unopened closing tag is dropped, and reasoning that ends in one short unit repeated for 2048 bytes is stopped, with stop reason `reasoning_loop` (no Python counterpart) and `[the model's reasoning was repeating itself; stopped it]`. Python shows no reasoning, so it neither shows the tags nor stops the loop, and waits for the cap.

- `[providers.<name>.routing]` (a deliberate addition): sent as the request's `provider` field, for OpenRouter's provider routing. Python sends no such field.

- Ollama's context window (a deliberate change, 2026-10-29): Python always asks for `num_ctx = 8192`, its built-in default, and reports that as the window, whatever the model supports. Rust has no built-in `num_ctx`; it asks `/api/show` (memoized per process, never cached on disk) and sends the `num_ctx` the model's Modelfile sets (its `parameters`), as it is, because someone chose that size for that model; without one, the smaller of the trained `<architecture>.context_length` and `[providers.ollama] num_ctx_max` (default 32768, because Ollama allocates the whole window and a model's full 256k can leave the GPU). Sending the capped figure would override the Modelfile, since a request's `num_ctx` wins over it: the first version did, and ran a model built with `PARAMETER num_ctx 262144` (`qwen3.5:9b-262k`) at 32768. The status line and compaction use the same figure. A `num_ctx` the user sets is sent as before, without asking the server, and when `/api/show` cannot say, 8192 is sent, as in Python. Live check (2026-10-29, Ollama 0.40.7, `qwen3.5:latest`, trained for 262144): `run` sent 32768, and `/api/ps` showed the model loaded at 32768.

- `Retry-After` HTTP-date values are not parsed; they fall back to exponential backoff. Delta-seconds values are honoured.
- Python retries only `ConnectError`, `ConnectTimeout`, and `RemoteProtocolError`. `reqwest` does not expose the same classes, so Rust retries any transport failure other than a read timeout, still only before text has been emitted.
- Like Python, an SSE `data:` chunk carrying an `{"error": ...}` object (sent by OpenRouter for mid-stream failures) is silently ignored. Both implementations should probably surface it; change them together.

## 6. Compatibility strategy

The Python implementation was the behavioral oracle while the rewrite was under way, and the contracts below stay compatible with it for what the two share. Compatibility is tested through observable behavior, not by copying implementation details.

Contracts to preserve include:

- CLI arguments, stdout/stderr separation, and exit codes
- `run --json` field names and failure behavior
- TOML configuration resolution and write-back semantics
- Provider streaming, stop-reason normalization, usage, and pricing behavior
- Tool schemas, validation failures, approvals, and result ordering
- Session persistence and resumability
- Flight-recorder and export formats
- Graceful degradation when optional capabilities are unavailable

Recorded provider responses were introduced with the first provider; parity is checked by fixtures generated from Python's sources and CPython rather than a differential harness (see the decision under Next actions). Existing Python tests should guide expected behavior wherever practical.

The Rust runtime should be designed around explicit async ownership and cancellation rather than reproducing the Python mixture of threads and event loops literally.

## 7. Credential and security policy

- API keys must never be pasted into chat, committed, or written to configuration files
- Live providers should resolve secrets from environment variables or an OS keyring
- Tests must use fixtures, mock servers, or explicitly scoped test credentials
- Secret-shaped values should be redacted from logs, traces, and error paths
- Live tests must be opt-in and should use the least expensive suitable model
- Rust memory safety does not replace SSRF defenses, sandboxing, path validation, or secret redaction

A feature request has been drafted for Kimi to support secure, native secret input for sandbox tasks. It has not been submitted through the user's account. This does not block development or deterministic testing.

## 8. Working principles

- Keep the Python implementation as the reference until Rust reaches proven parity
- Prefer small, tested vertical slices over large rewrites
- Do not claim performance improvements without benchmarks
- Do not broaden features during the compatibility port
- Keep credentials and live services out of the default test path
- Treat security behavior and failure paths as compatibility requirements
- Keep the repository honest about what is and is not implemented

Done (parts 1 and 2 by 2026-10-30, part 3 on 2026-10-31; planned 2026-10-29): secure secret entry, beyond Python. Developers often have to give an agent a key, a token, or a password, and typing it into the chat sends it to the provider and copies it into scrollback, the Ctrl+O transcript, the prompt history, `state_json`, episodes (which are recalled into later tasks), the trace, and OTel spans. The rule: **the model never sees a secret's value, only its name**; the harness holds the value and uses it for the model. The guarantee is that secrets stay out of transcripts, provider logs, traces, and memory. It is not protection against a hostile model, which could still get a transformed copy (base64, part of the value) past literal redaction; the README says so.

- **`request_secret` tool** (`name`, `reason`). It opens a masked entry and stores the value in a `SecretVault` the harness and its sub-agents share (a sub-agent may ask too; it uses the same prompt). The model gets back only a notice such as `Secret 'STRIPE_API_KEY' is available as $STRIPE_API_KEY in run_command and python_exec, and as ${secret:STRIPE_API_KEY} in file tools.` Declining or cancelling returns a plain refusal, as a declined approval does. Its schema has no Python model, so it is listed in the schema fixture as beyond Python.

With no terminal (piped input, CI) the tool is not offered at all, so those runs keep Python's tool list.
- **`/secret NAME`** opens the same entry without the agent asking, and the next request tells the model the name is available. `/secret` lists names (never values), and `/secret forget NAME` drops a secret from the vault and the keyring.
- **Environment injection.** `run_command` and `python_exec` add vault entries to the child's environment after `scrubbed_env`. The scrub of inherited credential-shaped names does not change; a vault entry gets in because the user granted it explicitly.
- **`target`, dropped (2026-10-29).** It was to make `request_secret(name, target=".env")` write `NAME=value` itself. Placeholders do the same through `write_file` or `edit_file` (`API_TOKEN=${secret:API_TOKEN}`), with the approval, the diff, and the jail those already have, so a second write path would only add surface.
- **Placeholders.** `${secret:NAME}` in `write_file` and `edit_file` arguments is expanded when the tool runs, after approval. The approval preview, the diff the user sees in the transcript, the trace, and the stored tool call keep the placeholder; an unknown name fails the call with a message naming it. Expansion happens in the harness's dispatch, not in each tool, so a tool added later cannot skip it, and MCP tools never get vault values.
- **Redaction on the way out.** Every vault value joins the literal set passed to `secrets::redact` on four paths: tool results before the model sees them (so `cat .env` comes back redacted), streamed model text, `redact_event` before the trace, and saving `AgentState` and recording episodes. The session database holds only names, so `state_json` stays readable by Python.

At startup, remembered names are loaded into the vault, and the system message lists the available names. Without a keyring the toggle is shown as unavailable and the secret stays in the session. Done (2026-10-31, for 1.0.10; planned the same day): show or hide thinking and tool use in the interactive interface, beyond Python. Thinking models stream a lot of reasoning, and tool-heavy turns print a line per call; some users want that quiet, others want more. Status: implemented, as the next feature ahead of scheduled jobs (below), because it was the smaller change (decided 2026-10-31); the as-built differences from the design are listed after it. Decided with the maintainer:

- **Two settings, three levels each.** Thinking: `full` (streamed dimmed under `∴`, as now), `summary` (one dim line, `∴ thought for 12s · 2.1k chars`, printed when the reasoning ends), or `hidden`. Tool use: `full` (the call's arguments and the whole result, inline), `summary` (one line per call, as now), or `hidden`. The `full` result is not capped (the maintainer's choice), so one `read_file` at `full` can scroll everything else away; it is opt-in, the Ctrl+O transcript has the same text at any level, and a cap can be added if it proves a problem.
- **Defaults are quieter: thinking `summary`, tool use `summary`.** Today thinking is `full`, so this changes what existing users see after the upgrade; the release notes must say so and name the setting that restores it (`[ui] thinking = "full"`). Recorded as a deliberate difference (Python ignores reasoning altogether).
- **Controls: a hotkey, commands, and config.** Ctrl+T cycles thinking (`full`, `summary`, `hidden`), the control wanted mid-turn; Shift+Tab, Ctrl+O, Ctrl+C, Esc, and the editor's readline keys stay as they are. Tool use has no hotkey. Proposed names, to confirm when built: `/thinking [full|summary|hidden|save]` and `/toolview [full|summary|hidden|save]` (a bare command shows the level), `save` writing the session's choice to `[ui] thinking` and `[ui] tool_use` through `config_writer`'s diff panel, as `/limits save` does. The settings are `[ui] thinking` and `[ui] tool_use`; Python ignores unknown keys, so shared config files stay compatible, and an unknown value is a config error naming the allowed ones.
- **Hidden still tells the user what matters.** A failed tool call, a declined approval, and every approval prompt always show, even with tool use `hidden`, since hiding them would hide why a turn went wrong or stalled. The live status line keeps showing `thinking` and the tool's name while they run. The Ctrl+O transcript keeps everything (full thinking, every tool call with arguments and result) whatever the levels, so hiding is display-only: the entries are recorded in full, and the trace and the session are untouched.
- **Interactive interface only.** `run`, `run --json`, and the plain loop print exactly what they do now, since their `[tool] ...` notices are part of the output streams the plan keeps compatible with Python; no flag or variable changes them.
- **A change applies from then on.** Scrollback cannot be re-rendered, so what is already printed stays; the unfinished thinking tail in the live region follows the new level at once, and blocks committed afterwards use it.

Design notes: the levels live in `App` (the state machine, so tests drive them with key and turn events, with no terminal), set from `[ui]` at startup; `drain_thinking` and `finish_thinking` honour the thinking level (`summary` needs the time of the first reasoning delta and a character count, kept per block and reset in `finish_thinking`), and the tool-call and tool-result commits honour the tool level, with failures and approvals bypassing it. The `[ui] tool_use` and `[ui] thinking` values are a small `enum` in `config.rs`, shared by the settings and the commands. Tests: each level's output for thinking and for tool use; a failed call and an approval shown at `hidden`; the status line while hidden; the transcript entries holding the full text at every level; Ctrl+T cycling and wrapping; the commands (a bare one reports the level, a bad value lists the choices, `save` writes only the changed key); the config's defaults, valid values, and rejection; the summary line's wording (seconds, and sizes below and above 1000 characters, `1.2k`); and the existing `run` and plain-loop tests unchanged, as proof they are untouched. Slices: (1) the settings, the config values, and the commands; (2) the thinking levels and the summary line; (3) the tool levels; (4) Ctrl+T and the status hint; (5) `save` through the diff panel; (6) the README, this plan, and the release notes' upgrade warning.

As built (2026-10-31), where it differs from the design: `DisplayLevel` (`full`, `summary`, `hidden`) is in `config.rs`, and `src/ui/display.rs` holds the commands, `save`, and `on_saved`; the levels live in `App` (`set_thinking_level`, `set_tool_level`), and `SavePurpose::Display` carries the save. The command names are `/thinking` and `/toolview`, with `[level|save]` as their usage; `save` from either command writes whichever of the two levels differs from the config (and says so when none does), and the plain loop's copies only say they are interface settings. Ctrl+T and the commands print a dim note (`thinking: hidden`) instead of a status-line hint, since the status line is already crowded and sheds segments by width. `full` prints the arguments and the whole result inline, uncapped as decided, but the Ctrl+O transcript keeps Python's 200-line result cap (`RESULT_LINE_LIMIT`), so at `full` the screen can hold more of a long result than the transcript view; the design said they would match. Planned (2026-10-31, after the show/hide thinking and tool use feature above): scheduled jobs, beyond Python. Let the model create durable recurring or one-shot jobs ("every morning at 9, do X in this workspace") and have agent86 itself fire them and run a real agent turn to do the work, even when no interactive session is open. The agent schedules work for itself; agent86 executes it. Python has no scheduler, so there is no compatibility surface to preserve, and the change is recorded here as a deliberate addition. Status: design only, nothing implemented. The design decisions, and why:

- **Where jobs live: a file, not the memory database.** Definitions go in `~/.agent86/schedule.json` (`[schedule] path` overrides it), written atomically (temp file and rename, the pattern `update.rs` and `config_writer` use). That decouples the scheduler from the memory subsystem (which needs an embedder built and is off when `[memory] enabled = false`) and leaves the Python-shared SQLite schema alone. A job's runs still land in the memory database as ordinary sessions and episodes; only the definitions are in the file. A `jobs` table in `memory.db` was rejected for the same coupling.
- **Who fires jobs: a resident daemon.** `agent86 schedule daemon` is a long-running process that loads the job list, sleeps until the next fire time, and runs each due job. It is the only mechanism that works with no session open, which is the actual "every morning at 9" case. Two secondary mechanisms are deferred: an in-process check in the interface's 50 ms `pump` (short reminders while agent86 is in use, with the job's side effects approvable at the terminal), and an OS trigger (the agent installs a cron or Task Scheduler entry through `run_command`), documented as an option and never automatic, since it is platform-specific and fragile.
- **Schedule forms: `at`, `every`, `daily_at`; no cron parser.** `at` is a one-shot RFC 3339 timestamp, `every` an interval in seconds, `daily_at` an `HH:MM` in a timezone (`chrono::Local` by default, an explicit offset optionally). That covers the common cases without a cron dependency (the crate is deliberately lean on dependencies); cron can come later.
- **Execution: a fresh, cost-capped, unattended turn per fire.** The daemon assembles a harness for the job's `workspace`, `model`, and `approval` and runs `Harness::run_turn` with the job's `task` as the goal, in a fresh session (bounded context and no drift across runs; continuity comes from the memory database's episode recall plus a short note of the last run's outcome). Approval defaults to `auto`, since nobody is there (`ask` would decline with no prompt, which is the safe behaviour for a job that asks for it). Every run is bounded by the existing `CircuitBreaker` (`max_steps`, `max_cost_usd`, `max_wall_clock_s`, `max_consecutive_errors`). One job runs at a time, and a lock file (`~/.agent86/schedule.lock`) also stops two daemons double-firing.
- **Missed fires.** On daemon start, each enabled job's next fire is computed from its last run. A recurring job whose next fire is in the past fires once, then advances to the first occurrence strictly after now (no burst of catch-up fires). A one-shot job fires once if it was missed by less than a grace window (`[schedule] grace_s`), else it is marked `missed` and disabled.
- **Security: creation is approval-gated and everything is visible.** `schedule_create` is side-effecting, so the user approves the definition (task, schedule, workspace, model) before it is persisted; a model cannot silently install a recurring action. Jobs are always inspectable and removable by the user (`agent86 schedule list|show|cancel`, later a `/schedule` panel). A job's task text passes through the ingress guardrail like any goal. A job run has no session secrets (unattended, so `request_secret` is not offered); provider keys come from the keyring as usual, which is a documented limitation. The daemon refuses to run a job whose workspace is gone or whose model cannot be built, records a failure, and never guesses.

Decided with the maintainer (2026-10-31), settling the open questions and widening the scope:

- **Everything ships in one release**, including the service install and notifications below; the phases are ordered so each is still a testable slice.
- **`agent86 schedule install-service` and `uninstall-service`** (new): a user-level service that starts at login and runs as the user, so it has the user's keyring: a systemd `--user` unit on Linux, a launchd LaunchAgent on macOS, and a Task Scheduler task at logon on Windows. No admin rights and no system-wide change (a boot-time service was rejected: the OS keyring that holds provider keys is not available before login, so jobs would run without API keys). `src/service.rs` writes and removes the entry; the unit's text is pure and tested, and nothing in the default tests registers a real service.
- **Desktop notifications, on every run** (success and failure, for every job), by shelling out to the OS tools: `osascript` on macOS, `notify-send` on Linux, a PowerShell toast on Windows. No new dependency, so no MSRV (1.88) or five-target build risk. A missing tool (a headless Pi has no `notify-send`) is logged and skipped, never fatal. `src/notify.rs` builds the command; tests check the command lines, never send one. A per-job `notify = false` to quiet a frequent job is the obvious follow-up if every-run proves too noisy, but is not in this release.
- **Per-job approval, set at creation.** Each job stores `approval` (`auto`, or `deny` for a read-only job); the user approves the whole definition when the model creates it, and the approval prompt names what the job may do. `auto` stays the default the design had; `deny` is the easy safe choice.
- **Schedule forms as designed:** `at`, `every`, and `daily_at`, no cron parser, no weekly form. A later form does not change stored jobs.
- **Results:** each run is an ordinary session in the memory database, the daemon appends to a log file, `agent86 schedule show <id>` prints the last run's output, the interface prints a note on its next start for runs since it last looked, and a notification is sent as above.
- **Command name:** `agent86 schedule daemon`, with `list`, `show`, `cancel`, `run`, `install-service`, and `uninstall-service` beside it.
- **No secrets in jobs in this release.** A job gets provider keys from the keyring and environment as usual and nothing else; a job naming remembered secrets is a possible later extension.
- **Model:** chosen at creation (`provider:model`, shown in the creation approval), else `[schedule] default_model`, else the configured default.

Components, by file: `src/schedule.rs` (new: the `Job` model with id, task, schedule, workspace, model, approval, `created_at` and `created_by`, `enabled`, `last_run_at`, `last_run_status`, `last_run_output`, and `run_count`; the schedule math `next_fire(now)` and `advance_after(fire_time)`; the `Scheduler` store with load, atomic save, and the lock file; the daemon loop and `run_job`: assemble the harness, run the turn, record the result, persist, and emit the trace event and episode); `src/tools/schedule.rs` (new: `schedule_create`, side-effecting, plus read-only `schedule_list` and `schedule_cancel`, and perhaps `schedule_run`; a `Scheduler` handle rides on `ToolContext` the way `memory` does); `src/setup.rs` (`assemble` takes an explicit workspace instead of hardcoding `current_dir()`, so the daemon can jail a harness to the job's workspace; existing callers pass `current_dir()`); `src/tools/mod.rs` (register the schedule tools in `default_registry` when the feature is on, and add the `Scheduler` field to `ToolContext`); `src/main.rs` (the `schedule` subcommand: `list`, `show <id>`, `cancel <id>`, `run <id>` to run one now for testing, and `daemon`); `src/config.rs` (a `[schedule]` section: `enabled`, `path`, `max_concurrent` with default 1, `grace_s`, a `log` path, and `default_model`); `src/observability.rs` (new trace events `job_created`, `job_run` with status, usage, and cost, and `job_missed`, redacted like all others); `src/repl.rs` and `src/ui/` later (a `/schedule` command, a schedule panel, and the in-process due-job check); and docs: the README status and roadmap, this plan, CLAUDE.md's architecture notes, and a new ADR 0002, since this is a significant design decision, as ADR 0001 was for the interface.

Phases, each a testable vertical slice: (1) the job model, the schedule math, and the store: pure, with no I/O beyond the file; (2) execution and `schedule run <id>`: `run_job` over the refactored `assemble`, `run_turn`, persistence, and the trace event; (3) the daemon: the loop, the lock file, catch-up on start, one job at a time, and a clean shutdown on Ctrl+C; (4) the tools: `schedule_create` (approval-gated, writing to the store), `schedule_list`, and `schedule_cancel`; (5) the `[schedule]` section, the `job_*` trace events, the run log, and the interface's note for runs since it last looked; (6) desktop notifications (`src/notify.rs`); (7) `install-service` and `uninstall-service` (`src/service.rs`); (8) the docs, the ADR, and this plan.

Tests, in the repository's style (no network or credentials, the mock provider and recorded fixtures, an isolated `HOME`/`USERPROFILE` and working directory as in `tests/cli_run.rs`): the schedule math is pure, so exhaustive unit tests of `next_fire` and `advance_after` for all three forms across timezone boundaries, DST, and the catch-up rules (the cheapest, highest-value tests); the store's round trip, an atomic write (a crash mid-write simulated), and lock contention; the daemon with a short `every` job against the mock server, asserting that it fires, advances, does not double-fire, catches up once, and shuts down cleanly; `schedule run <id>` through the binary, asserting the turn ran, the session persisted, and the result was recorded; the tools, with creation refused under `deny`, approved under `auto` or `ask` with a prompt, landing in the store, and the model seeing only the job's fields and never a secret; and the failure paths (a bad model, a missing workspace, a cost-cap trip), each recording a clean failure without a panic.

Risks and open questions: a resident daemon does not fire while the machine sleeps, so the catch-up rule covers "I was asleep at 9am", but the OS-trigger option is the robust answer for a hard deadline, and the docs should say so plainly. Building a harness (the provider and any MCP servers) for every fire is correct but wasteful for frequent jobs; the first version builds and drops one per run, and a later one could pool harnesses keyed by `(workspace, model)`. Unattended runs under `auto` approval are the real risk surface: approval-gated creation, visibility, the cost caps, and the ingress guardrail mitigate it, but a buggy or malicious model can still schedule something the user approved once, so the ADR should state the threat model. Jobs cannot use session secrets, only keyring and environment provider keys (remembered secrets, 1.0.9, are per project and loaded only at a terminal, so they are not available to the daemon either; decided above: no secrets in jobs in this release). The service install and the notifications are the platform-specific parts, so they are the likeliest to need fixes after the first real run on each OS, and the release notes should say which platforms were run live.
