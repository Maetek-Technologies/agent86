# 0003. agent86's harness is offered as an embeddable agent API, starting inside the crate

## Status

Accepted — 2026-11-19 (proposed the same day with the prototype; accepted once the fourth slice, the mid-turn callbacks and `Conversation`, completed the API the crate split will publish)

Amended — 2026-11-19: the crate split landed, with a two-tier public surface in place of the `pub(crate)` plan; see "Amendment: the crate split" at the end.

## Context

agent86 is built as a library with a thin command line on top: `src/lib.rs` exposes every module, and the CLI, the interactive interface, and the ACP server all run one `Harness` through `run_turn_events`. The pieces another program would need to build an agent of its own are already traits (`Provider`, `Tool`, `Embedder`, `SecretStore`, ACP's `Backend`), and the test suite already builds harnesses by hand from injected parts.

What sets that harness apart from the agent frameworks people embed today (LangGraph, CrewAI, AutoGen, the OpenAI Agents SDK, Pydantic AI) is not orchestration but what happens when an agent acts on a real machine: the workspace jail, the approval gate that declines when nobody can be asked, the scrubbed and deadline-bound sandbox, the SSRF-guarded fetch, the guardrails, and the secret vault whose values the model never sees. Those frameworks leave most of that to the user. A program that wants those properties today has to shell out to `agent86 run --json` or speak ACP to a subprocess.

Using the crate directly is not practical yet:

- **Assembly assumes the CLI's world.** `setup::assemble` reads the merged config, the home directory (skills, specialties, approvals, traces, memory), the keyring when there is a terminal, and the process's current directory. An embedding program wants none of that unless it asks.
- **Everything is `pub`, nothing is promised.** Most public items are public for the integration tests and the binary. Their signatures change freely, and `Cargo.toml` says `publish = false`.
- **Shared-format types leak.** `AgentState`, `TurnSummary`, and the trace events carry Python's field names and quirks because the session database and trace are shared with the archived Python implementation. Those are CLI compatibility contracts and should not become a library's semver surface by accident.
- **No driving surface of its own.** Building a `Harness` struct literal means filling eighteen fields, several of which (the prompt queue, the vault's queue, the cancel token) must be wired to each other.

Questions this had to settle:

- Whether to split the crate first, or prove the API inside it.
- Which parts an embedded agent gets by default, and which it must ask for.
- How approvals work with no terminal.
- What the public surface is, and how it is kept apart from the CLI's compatibility types.
- What stays out of scope: orchestration graphs, bindings for other languages.

## Decision

**Ruling:** agent86 offers its harness to other programs through a small builder API (`agent86::sdk`: `Agent::builder()`, `Agent::run`, `FnTool`), first as a module of the existing crate and later as the public face of a separate `agent86-core` crate. It assembles the same `Harness` from parts the caller hands it, reads no config, environment, home directory, keyring, or terminal, and keeps every safety default of the CLI.

What that means:

- **Prototype inside the crate, split later.** `src/sdk.rs` builds the `Harness` directly, beside `setup::assemble`, so the API can be tried without moving forty modules. The split into `agent86-core` (types, providers, loop, tools, approvals, guardrails, sandbox, vault, memory, MCP) and `agent86` (the binary: interface, REPL, `keys`, `auth`, update, ACP) happens once the API has settled and is a separate change with its own review, because it touches CI, the npm build, and every `use crate::` path.
- **Explicit in, nothing implicit.** `build()` needs a provider and a workspace path and reads nothing else. A missing workspace is an error, never the process's current directory. Defaults (step, cost, wall-clock, output, and tool-time limits; guardrail modes) come from the CLI's built-in config text through `config::builtin_config()`, so they live in one place.
- **Least authority by default.** No built-in tools unless asked (`Builtins::None`, then `ReadOnly`, `Files`, `All`, each including the previous one). Approval mode `ask` with no approver declines every side-effecting call, exactly as a piped `agent86 run` does. An `approver` closure gets the tool's name and the same `ApprovalPreview` (arguments, diff) the terminal and ACP show, through the same one-at-a-time prompt queue.
- **Same harness, same guarantees.** The loop, circuit breaker, jail, gate, guardrails, vault redaction, parallel read-only calls, context fitting, compaction, and the `TurnEvent` stream are the harness's own, not reimplemented. The trace is off unless `trace_dir` is given, and then it is redacted as the CLI's is.
- **MCP servers and memory are given as parts, not config** (second slice, 2026-11-19). `mcp_server(name, McpServer)` starts a server with the agent on a manager attached to its registry; every value (arguments, environment, URL, headers) is literal, because `${VAR}` expansion reads the process's environment and the keyring, which an embedding program has not offered (the rule the ACP server follows for an editor's servers). A server that fails to start, a repeated name, or a tool collision fails `build()` rather than becoming a note, since the caller asked for the server by name; drops, reconnects, and tool-list changes after start are kept as `Agent::notes()`. `memory(Memory)` takes an opened database (`Memory::open` with the offline hashing embedder, `open_with` for another embedder, `in_memory`) shared by clones; with it the harness saves the session after every step, `Agent::run` saves it after every turn, failed ones included, finished turns are recorded as episodes and recalled into similar later turns, `remember` and `recall` are offered, retention runs at `build()` with the CLI's caps unless `Memory::retention` changes them, and `session(id)` resumes any saved session, the CLI's included, since the file and schema are the same.
- **Skills, sub-agents, routing, and spans are given as parts too** (third slice, 2026-11-19). Nothing is discovered: no `.agent86/` or `~/.agent86/` directory and no `OTEL_*` variable is read. `skills_dir` names the directories skills come from (the first wins a name, as discovery's roots do; `skills::discover_in` is the shared rule), and their folders join the jail for reading. `subagents(SubAgents)` turns on `delegate` with the CLI's depth, step, and parallel defaults, agent86's built-in specialists unless `without_built_ins`, and the caller's own through `specialists_dir`, read as user definitions (`Specialties::add_user_dir`): the caller vouches for them, so no per-file approval applies, which is why the documentation warns against passing a repository's directory. `model(name, Model)` names models; the router is given a lookup instead of a builder, so a specialist's `model:` resolves by name with or without `triage(cheap, frontier)`, which turns on triage routing. `otel(Otel)` takes an OTLP/HTTP traces URL with headers and a timeout, or the console. A turn is a `Turn`: a goal (a string converts), `Turn::skill`, or `Turn::specialist`, run through `Harness::run_kind` as every surface does, and an unknown skill or specialist is a `RunError` before any model call.
- **Questions a turn asks are callbacks** (fourth slice, 2026-11-19). `on_limit` installs the harness's limit hook (`SessionLimits::prompt`): given the `LimitHit`, it returns the new limit or `None`, which stops as before. `on_secret_request` installs the vault's prompt and offers `request_secret`; the callback returns the value or `None`, and nothing is remembered in a keyring, since the API reads none. `secret(name, value)` holds a value the program already has, through `SecretVault::accept`, so the vault's rules (valid name, `MIN_SECRET_CHARS`) apply and a refusal fails `build()` with a message that names the secret, never its value. Both kinds reach tools as environment variables and the model only as `${secret:NAME}`, through the same redaction the CLI uses. All three go through the prompt queue, one question at a time with approvals.
- **Left out:** project specialties' per-file approvals (the caller passes only directories it vouches for) and `/model`-style switching mid-session (a caller builds another agent with the conversation instead).
- **A narrow public surface.** `agent86::sdk` is the API that will carry semver once the crate is published. Until the split, the rest of the crate stays `pub` for the tests and the binary but is documented as unstable, and `Agent::harness()` is the escape hatch, also unstable. After the split, items not needed by `sdk` become `pub(crate)` or `#[doc(hidden)]`.
- **Compatibility types stay behind the API.** A conversation is a `Conversation`, which wraps `AgentState` without exposing it: `id`, `messages` (the API's own `ConversationMessage`: role, text, tool calls, the call a result answers), `steps`, `usage`, `last_turn`, and `to_json`/`from_json`, whose JSON is the session database's `state_json`. `Agent::conversation` and `with_conversation` replace the prototype's `state` and `with_state`. `RunResult` is the API's own type. `TurnSummary`, `Usage`, `Role`, `ToolCall`, `LimitHit`, `LimitKind`, and `SecretRequest` are re-exported from `sdk`, so its users name no other module; they are plain data, but they do become part of the library's semver once it is published.
- **No orchestration engine.** agent86 positions itself as the runtime that executes safely, not a graph planner. Programs compose `Agent`s in their own code, and other orchestrators can use agent86 as their executor through this API, MCP, or ACP. A workflow engine would be a separate ADR.
- **Rust first; bindings later.** Python (PyO3) and TypeScript (napi-rs) bindings over `sdk` are where most agent builders work, and are the main reason to keep the surface small and owned types only. They are a separate decision, made after the API settles.

## Consequences

- **Other Rust programs can embed agent86** with a provider, a workspace, and a few closures, and get its sandbox, approvals, guardrails, and redaction without running a subprocess. `tests/sdk.rs` builds agents from a provider written against the public trait, with no network, and checks custom tools, failures reported to the model, conversation continuation and state round trips, approvals with and without an approver, the jail, the step limit, and build refusals; skills (offered, run directly, `allowed-tools` enforced); sub-agents (a plain delegation, a caller's specialist run directly with only its tools, a skipped definition reported, a specialist on its named model); triage between two named models; spans at a mock OTLP collector; MCP tools from the stdlib-only fixture server (mounted, gated by their read-only hint, values kept literal, a crash failing the build); and memory (a session saved and resumed, a finished turn recalled into a new session, `remember` offered). `examples/embed.rs` runs against any OpenAI-compatible endpoint.
- **Two assembly paths exist until the split.** `setup::assemble` (config-driven, for the binary) and `sdk::AgentBuilder::build` (explicit) both fill the `Harness` struct, so a new required field must be added to both. A later step makes `setup` build on the builder, so there is one path again.
- **Nothing is promised yet.** `publish = false` stays until the crate split. The README does not advertise the API until then.
- **The CLI's contracts are untouched.** `run --json`, the session database, the trace format, and the config semantics do not change. `config::builtin_config()` is the only addition outside `sdk`.
- **Tools still run synchronously inside the turn's runtime**, as they do for the CLI. An embedding program on a multi-threaded runtime is fine. A tool that blocks for long holds the turn, as it always has. An async `Tool` trait is a possible later change, not part of this decision.
- **It sharpens what agent86 is for.** The pitch becomes "the agent runtime you can safely point at a real machine", which the CLI, the editor integration, and the library all share.

## Amendment: the crate split

**Ruling:** the library is `agent86-core` (`crates/agent86-core/`) and the binary stays at the root as `agent86`. `agent86_core::sdk` is the only surface with a stability promise; every other module stays `pub` for the binary but is `#[doc(hidden)]`, and the binary uses the library by path, so the two always build from the same checkout and ship at one version. ([docs/crate-split.md](../crate-split.md) has the sketch and what was built.)

**Why the decision changed.** The Decision above said that after the split, items not needed by `sdk` would become `pub(crate)` or `#[doc(hidden)]`. Measuring first ruled out `pub(crate)`. The binary's surfaces use 137 distinct library items and call the harness directly 127 times: the ACP server and the interface drive it themselves, and `setup` fills its fields from config. Making those private would mean rebuilding the CLI on `sdk` first. So the binary is treated as an in-repository user of an unstable second tier, and the two always ship at one version, from one checkout.

**What it means:**
- **Re-exports in both directions.**
  - `sdk` re-exports every type its own signatures use, and `sdk::providers` holds the `Provider` trait, its types and the built-in adapters. An embedder never names a hidden module, which the SDK's tests and example now show by importing only from `agent86_core::sdk`.
  - The binary's `lib.rs` re-exports the library's modules under their old names, so its code and tests moved without import changes.
- **The library never depends on the binary.** The one dependency that pointed that way, the terminal secret prompt reading hidden input through `keys`, moved to the binary with `setup`, its only user.
- **The heavy parts are optional.**
  - `os-keyring` gates the keyring stacks for each OS; without it a lookup reads as "no key stored".
  - `local-embeddings` gates candle and tokenizers; without it a `sentence-transformers:` spec falls back to the hash embedder with Python's `ImportError` note.
  - Both are on by default. Turned off, the library's dependency tree drops from 367 crates to 172, and CI runs its unit tests that way on every OS.
- **Published (1.1.0).** `agent86-core` is on crates.io, published by the release workflow on each tag after the binary archives, at the same version as the CLI. Its documentation on docs.rs shows `sdk` only, and its README says that only `sdk` is covered by semantic versioning: a breaking change there needs a new major version, while the hidden tier may change in any release. The binary is not published.
- **Narrowing later is still possible.** It can happen one surface at a time, by moving what a surface needs behind `sdk`. Each step shrinks the hidden tier without breaking the stable one.
